# RGB-D 跟踪路线说明

## 1. 结论

RGB-D 跟踪不是单一项目，而是一整条技术路线。

它的核心判断是：

1. RGB 负责外观。
2. Depth 负责空间。
3. 两者必须联合做跟踪判断。

对本项目来说，RGB-D 路线是最接近“颜色 + 深度并行”的方向。

## 2. 参考依据

GitHub 参考：

- RGB-D 跟踪综述索引: https://github.com/983632847/Awesome-Multimodal-Object-Tracking
- DepthTrack/DeT: https://github.com/xiaozai/DeT
- SMART-TRACK: https://github.com/mzahana/SMART-TRACK

相关数据和基准：

- DepthTrack
- VOT-RGBD
- RGBD1K
- ARKitTrack

这些资料共同说明：RGB-D 跟踪现在的主流不是单独看深度，也不是单独看颜色，而是做融合和门控。

## 3. 适配思路

RGB-D 跟踪路线对本项目最重要的三点是：

1. 深度不是附加信息。
2. RGB 和深度必须并行传递。
3. 深度缺失时必须自然退化。

所以本项目不需要重新发明一个纯 RGB tracker，也不需要做三套 tracker。
更合理的是：

- 一套主 HiT
- 一套几何层
- 一套 DTC
- 一套轻量融合头

## 4. 这条路线里的常见做法

### 4.1 颜色与深度的关系

- 颜色做外观匹配。
- 深度做边界和遮挡判断。
- 运动状态做连续性判断。

### 4.2 融合位置

常见融合位置有三种：

1. 输入级融合。
2. 特征级融合。
3. 分数级融合。

对本项目来说，最合适的是分数级融合，再逐步升级到轻量特征融合。

### 4.3 预测方式

RGB-D 跟踪路线里，最常见的状态预测方式还是轻量状态模型：

- 常速度模型
- Alpha-Beta
- Kalman Filter

这与本项目的 DTC 很一致。

## 5. 实施步骤

### 阶段 1：定路线

目标：明确 RGB-D 在本项目中不是附属项。

工作项：

1. 统一 `FramePacket` 的 RGB / Depth 结构。
2. 统一 `LocalView` 的 RGB / Depth 结构。
3. 统一 `DTC` 的深度门控规则。

验收：

- 文档和接口统一。

### 阶段 2：定融合层

目标：把 RGB-D 变成可控融合，而不是多模型堆叠。

工作项：

1. 设计 `depthScore`。
2. 设计 `motionScore`。
3. 设计 `scaleScore`。
4. 设计轻量融合头。

验收：

- 能对候选做统一打分。

### 阶段 3：定退化层

目标：保证没有深度也能跑。

工作项：

1. 深度缺失时深度权重归零。
2. `DTC` 退化为 RGB + 球面几何。
3. `HiT` 继续工作。

验收：

- `rgb_only` 与 `rgb_depth` 都可运行。

## 6. 风险点

1. RGB-D 路线本身太宽，不能直接拿来当单个实现方案。
2. 特征级融合训练成本高。
3. 输入级融合容易破坏深度语义。

## 7. 最终建议

对本项目而言，RGB-D 路线最合理的落点是：

1. 颜色和深度并行传递。
2. DTC 做轻量状态预测。
3. HiT 做外观匹配。
4. 融合头做最终决策。

它不是一个单独替代项，而是本项目主架构的基础方向。
