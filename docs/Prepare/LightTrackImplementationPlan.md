# LightTrack 全景跟踪实施方案

## 1. 结论

LightTrack **有可行性**，但只能作为“轻量单目标跟踪核心”，不能直接等同于整套全景跟踪方案。

原因很简单：

1. 官方 LightTrack 面向的是常规视频单目标跟踪，核心优势是轻量和快。
2. 你的任务是 360 全景视频，存在经线跨越、投影畸变、极点失真和长时找回问题。
3. 所以正确做法是：**LightTrack 负责局部跟踪，全景几何模块负责裁剪与映射，恢复模块负责丢失找回。**

结论：**可做，而且适合做成比赛基线。**

## 2. 参考依据

官方仓库说明：

- 采用 one-shot architecture search 做轻量 tracker。
- 训练/测试主要基于 Python 3.6、`install.sh`、PyTorch 生态。
- 仓库内包含 `tracking/`、`experiments/`、`snapshot/`、`dataset/` 等目录，说明它本来就是一个可训练、可评测、可导出的研究代码库。

论文和仓库都表明它的目标是“更轻、更快的目标跟踪器”，这和你项目中的实时要求是匹配的。

## 3. 适配思路

不要直接拿 LightTrack 处理整张等距柱状图，而是做成三层结构：

1. **球面几何层**  
   负责 equirectangular 到局部透视视图的转换，处理 0/360 边界和 pitch 极区。

2. **LightTrack 跟踪层**  
   只在局部透视窗口中做跟踪，减少畸变影响，也减轻算力压力。

3. **丢失恢复层**  
   负责置信度判断、全景候选搜索、模板保护和目标找回。

## 4. 技术栈

### 4.1 语言

- **Python**：训练、推理脚本、数据处理、评测脚本。
- **CUDA**：如需加速算子或部署 TensorRT，可作为可选优化层。
- **Shell**：环境安装、训练启动、评测启动、Docker 入口脚本。
- **C++（可选）**：如果后续要做更稳定的端侧部署或 CMake 原生程序入口，可以加一层 C++ 推理壳。

### 4.2 框架与工具

- **PyTorch**：主训练框架。
- **OpenCV**：视频读取、图像裁剪、坐标变换、可视化。
- **NumPy**：几何计算、框格式转换。
- **ONNX / ONNX Runtime**：模型导出和轻量推理。
- **TensorRT（可选）**：如果决赛环境支持 GPU，可进一步加速。
- **CMake**：如果项目最终要统一成 C++/混合工程，则用来组织构建。
- **Docker**：比赛提交封装。

## 5. 实施步骤

### 阶段 1：跑通 LightTrack 基线

目标：先让单目标跟踪流程跑起来。

工作项：

1. 下载并整理 LightTrack 官方代码。
2. 用官方权重或可用预训练权重验证普通视频跟踪效果。
3. 做统一输入输出接口，封装成 `track(frame, bbox)` 形式。
4. 输出每帧预测框和置信度。

验收：

- 普通视频能连续输出框。
- 单帧推理时间满足实时性预期。

### 阶段 2：加入全景几何适配

目标：让 LightTrack 适应全景视频。

工作项：

1. 将初始框中心转换到球面坐标。
2. 根据目标中心裁剪局部透视视图。
3. 处理经线跨越，保证目标移动连续。
4. 把局部框反投影回全景坐标。

验收：

- 目标穿过左右边界时不跳框。
- 高纬度区域的漂移明显减少。

### 阶段 3：加入丢失恢复

目标：解决长时遮挡和重新找回。

工作项：

1. 计算 LightTrack 输出置信度。
2. 低置信时暂停模板更新。
3. 触发全景多方向候选搜索。
4. 找回后恢复局部跟踪状态。

验收：

- 遮挡后可以重新找到目标。
- 误跟概率明显下降。

### 阶段 4：性能优化

目标：满足比赛部署和速度要求。

工作项：

1. 导出 ONNX。
2. 优化输入尺寸和搜索窗口。
3. 控制裁剪频率和全局搜索频率。
4. 必要时做 TensorRT 或半精度推理。

验收：

- FPS 达到评测要求。
- 精度不因加速明显下降。

### 阶段 5：工程封装

目标：可提交、可复现、可部署。

工作项：

1. 统一目录结构。
2. 统一配置文件格式。
3. 提供训练、验证、推理、导出、打包脚本。
4. 用 Docker 封装运行环境。

## 7. 风险点

1. **LightTrack 原生不懂全景畸变**  
   需要球面裁剪，不要直接喂整张 equirectangular 图。

2. **目标跨经线**  
   必须在球面坐标里做连续跟踪。

3. **遮挡后漂移**  
   必须做置信度门控和找回机制。

4. **端侧速度不足**  
   需要控制搜索窗口，并考虑 ONNX/TensorRT。

## 8. 最终建议

如果你想要一个**能尽快落地的比赛方案**，LightTrack 很适合作为第一版核心跟踪器。  
如果你想要的是**直接拿官方代码原封不动解决全景跟踪**，那不够，需要做上面的三层改造。

最稳的路线是：

1. 先用 LightTrack 跑通普通跟踪。
2. 再加全景几何适配。
3. 最后补恢复和加速。
