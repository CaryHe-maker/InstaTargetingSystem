# 面向 360 全景视频的实时单目标跟踪项目设计

## 1. 项目目标

本项目面向比赛题目“面向 360 全景视频的实时单目标跟踪”，目标是构建一个从“全景视频 + 初始目标框”到“逐帧目标位置”的完整跟踪系统，并最终封装为可提交的 Docker 镜像。

系统需要在等距柱状投影（Equirectangular）全景视频中，对指定单目标进行准确、稳定、实时的跟踪。核心指标以 OTB 协议为准，重点优化 Success Rate（IoU > 0.5）和 AUC，同时在决赛阶段兼顾算法帧率与方案解释能力。

## 2. 关键挑战

1. 投影畸变：目标在赤道和高纬区域的外观、形状、尺度变化明显，平面跟踪器直接使用会产生特征失真。
2. 经线跨越：目标从画面右边界移动到左边界时，像素坐标发生跳变，需要在球面坐标上保持连续运动建模。
3. 极点区域：接近 pitch = +/-90 度时，yaw 方向不稳定，目标外观剧烈变形，容易漂移。
4. 长时跟踪：遮挡、离开局部视野、相似目标干扰会导致跟踪器丢失，需要可靠的置信度判断与重新检测机制。
5. 实时性：全景帧分辨率高，不能对整帧进行重型全局推理，需要轻量模型和分层搜索策略。

## 3. 总体方案

初始方案采用“球面感知的局部跟踪 + 低频全局找回”的混合架构。

主流程如下：

1. 输入全景视频首帧和初始目标框。
2. 将目标框中心从图像坐标转换为球面 yaw/pitch 表示，并建立目标模板。
3. 在后续帧中，根据上一帧球面位置预测当前搜索区域。
4. 从等距柱状图中裁剪畸变较小的透视局部视图，送入轻量级单目标跟踪器。
5. 将局部视图中的跟踪结果映射回全景图像坐标，输出逐帧目标框。
6. 根据分类分数、响应峰值、尺度变化和运动一致性判断是否丢失。
7. 当目标疑似丢失时，启动多候选方向搜索或轻量检测器进行重新找回。

该方案优先保证工程可落地性：先实现一个稳定的 CPU/GPU 均可运行基线，再逐步加入球面增强、找回机制和推理优化。

## 4. 模块规划

### 4.1 输入输出模块

职责：

1. 读取视频帧、初始框和评测接口参数。
2. 统一内部框格式，例如 `x, y, w, h`。
3. 输出每帧跟踪框，满足比赛评测或 Docker 入口要求。

建议目录：

```text
src/io/
include/its/io/
```

### 4.2 球面几何模块

职责：

1. 图像坐标与 yaw/pitch 坐标互转。
2. 处理 0/360 经线跨越时的坐标连续性。
3. 根据目标中心和视场角生成透视裁剪视图。
4. 将局部视图框反投影回全景坐标。

建议目录：

```text
src/geometry/
include/its/geometry/
```

### 4.3 跟踪核心模块

职责：

1. 封装轻量级跟踪器接口。
2. 管理首帧初始化、模板更新、逐帧推理。
3. 支持后续替换不同模型，例如 SiamFC、LightTrack、NanoTrack 或 OpenCV 轻量跟踪基线。

建议先实现可运行基线，再接入深度模型：

1. 阶段一：OpenCV CSRT/KCF 或模板匹配基线，用于打通流程。
2. 阶段二：轻量 Siamese tracker，用于提升精度和速度平衡。
3. 阶段三：ONNX Runtime/TensorRT 后端，用于比赛提交优化。

建议目录：

```text
src/tracker/
include/its/tracker/
```

### 4.4 丢失判断与找回模块

职责：

1. 根据跟踪置信度、响应图质量、运动速度和尺度变化判断当前结果是否可信。
2. 对低置信帧暂缓模板更新，减少漂移。
3. 在目标丢失时进行多方向、多尺度候选搜索。
4. 找回成功后重建局部跟踪状态。

建议目录：

```text
src/recovery/
include/its/recovery/
```

### 4.5 评测与实验模块

职责：

1. 计算 IoU、Success Rate、AUC。
2. 统计 FPS、平均耗时、丢失次数和找回耗时。
3. 保存实验配置和结果，便于复现实验。

建议目录：

```text
tools/eval/
experiments/
```

其中 `experiments/` 默认不提交大文件，只提交必要的说明、脚本和小型示例配置。

## 5. CMake 工程结构

项目使用 CMake 管理构建，建议保持源码、头文件、工具和文档分离。

推荐目录结构：

```text
InstaTargetingSystem/
  CMakeLists.txt
  cmake/
  include/its/
  src/
  apps/
    tracker_app.cpp
  tests/
  tools/
  docs/
    ComRequire.md
    Design.md
  docker/
    Dockerfile
```

CMake 规划：

1. 根 `CMakeLists.txt` 定义项目名、C++ 标准和全局编译选项。
2. `src/` 构建为核心库，例如 `its_core`。
3. `apps/` 构建命令行入口，例如 `its_tracker`。
4. `tests/` 通过 `enable_testing()` 和 CTest 接入单元测试。
5. 第三方依赖优先通过系统包、CMake `find_package` 或清晰的依赖脚本管理，避免把编译产物和下载缓存提交到仓库。

## 6. 初始里程碑

### M1：工程骨架与基线跑通

目标：建立 CMake 工程、命令行入口、视频读取、初始框读取和逐帧输出。

验收标准：给定一个视频和首帧框，可以输出每一帧的预测框文件。

### M2：全景几何适配

目标：实现经纬度坐标转换、经线跨越处理和局部透视裁剪。

验收标准：目标跨越左右边界时，内部球面坐标保持连续，输出框不出现明显跳变。

### M3：轻量跟踪器接入

目标：接入可替换的跟踪器后端，先使用 OpenCV 跟踪器或模板匹配打通接口，再替换为轻量深度模型。

验收标准：在样例数据上可以稳定完成短视频跟踪，并输出基础 IoU 统计。

### M4：长时跟踪与目标找回

目标：实现低置信判断、模板更新保护和多候选找回。

验收标准：遮挡或短暂丢失后，系统能在限定帧数内恢复目标。

### M5：性能优化与 Docker 提交

目标：优化推理耗时，完成 Docker 镜像入口、依赖安装和自动化运行脚本。

验收标准：镜像可在评测环境中无人工操作运行，输出格式满足比赛要求。

## 7. 数据与模型管理

仓库只提交必要代码、文档、配置模板和小型示例。以下内容不提交到 Git：

1. 原始训练集、测试集、视频文件和解压后的数据目录。
2. 模型权重、导出的 ONNX/TensorRT Engine 文件。
3. CMake 构建目录、编译产物和 IDE 用户配置。
4. 实验日志、可视化输出、缓存文件和临时结果。

如需共享大文件，应使用外部存储或 Git LFS，并在文档中记录下载方式和校验信息。

## 8. 主要风险与应对

1. 畸变导致跟踪不稳定：使用局部透视裁剪降低输入畸变，并针对高纬度区域调整搜索范围。
2. 经线跨越导致运动模型失效：内部统一使用球面角度表示，输出阶段再转换为图像框。
3. 模板污染：低置信帧不更新模板，并设置尺度变化阈值。
4. 全局找回过慢：采用低频触发、粗到细搜索和候选方向优先级，避免每帧全景重检测。
5. 比赛接口未知：将输入输出、模型后端、配置读取做成独立模块，等官方接口开放后只替换适配层。

## 9. 当前优先级

短期优先完成可运行基线，而不是一开始追求复杂模型。建议下一步先补齐 CMake 工程骨架、最小命令行入口和基础几何工具测试，这样后续模型替换和 Docker 封装都会更稳。
