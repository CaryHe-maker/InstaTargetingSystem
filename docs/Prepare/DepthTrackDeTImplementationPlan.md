# DepthTrack/DeT RGB-D 跟踪实施方案

## 1. 结论

DepthTrack **是数据集和基准**，DeT **是建立在 DepthTrack 上的 RGB-D 跟踪基线**。

它们对本项目的价值非常高，因为它们说明了一件事：

1. 深度信息不是附属项。
2. 深度可以直接用于遮挡判断、边界修正和恢复搜索。
3. 只有 RGB-D 数据集，才足以把“深度真的有用”这件事验证出来。

结论：**DepthTrack/DeT 应作为本项目深度建模和融合设计的第一参考对象。**

## 2. 参考依据

官方资料：

- GitHub: https://github.com/xiaozai/DeT
- 论文页: https://openaccess.thecvf.com/content/ICCV2021/html/Yan_DepthTrack_Unveiling_the_Power_of_RGBD_Tracking_ICCV_2021_paper.html
- 测试集: https://zenodo.org/records/5792146

论文给出的关键信息是：

- DepthTrack 提供 200 个 RGB-D 跟踪序列。
- 数据规模和属性数量明显超过此前 RGB-D 跟踪集。
- DeT 不是把深度当旁路，而是把它作为 RGBD 跟踪的有效补充。

## 3. 适配思路

DepthTrack/DeT 对我们项目最重要的不是“直接照搬 tracker”，而是三点：

1. 深度应参与目标边界判断。
2. 深度应参与遮挡与恢复判断。
3. 深度应参与跟踪状态的置信融合。

因此，本项目可以借鉴的部分是：

- DTC 的深度权重设计
- 目标框内深度摘要
- BFoV 区域深度块
- 深度跳变门控
- RGB 与深度的结果融合

不建议直接照搬的部分是：

- 只适配普通针孔相机的局部跟踪流程
- 和全景 ERP 不兼容的固定裁剪逻辑
- 只适用于单一传感器的工程假设

## 4. 技术栈

### 4.1 语言

- Python：训练、测试、数据处理。
- PyTorch：模型与后处理。
- NumPy / OpenCV：图像和几何处理。

### 4.2 关键能力

- RGB-D 数据读取
- 目标框内深度统计
- 深度遮挡检测
- 恢复搜索区域生成
- 结果置信融合

## 5. 实施步骤

### 阶段 1：复现 DepthTrack 认知链

目标：先弄清楚 RGB-D 跟踪到底怎么用深度。

工作项：

1. 阅读 DepthTrack 论文。
2. 浏览 DeT 代码结构。
3. 明确深度在跟踪中的作用点。
4. 记录数据集属性和评测指标。

验收：

- 能说清深度是如何参与跟踪决策的。

### 阶段 2：抽取可迁移能力

目标：把 DepthTrack/DeT 的经验拆成可用模块。

工作项：

1. 提取框内深度摘要。
2. 提取边界深度变化。
3. 提取遮挡相关深度门限。
4. 提取恢复阶段的候选筛选逻辑。

验收：

- 可以映射到 `DTC` 和 `DepthProcessor`。

### 阶段 3：落入本项目接口

目标：把 RGB-D 经验接进现在的项目结构。

工作项：

1. `geometry` 同步输出 RGB 和深度视图。
2. `DTC` 消费深度摘要和 BFoV 深度块。
3. `tracker` 保留深度字段但可忽略。
4. `controller` 融合 RGB、深度和运动信息。

验收：

- 现有 `interface.md` 能直接承接这套逻辑。

## 6. 风险点

1. DepthTrack 是平面 RGB-D 跟踪，不是全景跟踪。
2. DeT 的裁剪和搜索策略不能直接用于 ERP。
3. 深度有效性依赖传感器质量。
4. 只看深度会丢外观信息，只看 RGB 会丢空间信息。

## 7. 最终建议

对本项目来说，DepthTrack/DeT 最适合承担：

1. 深度权重设计参考。
2. 深度摘要设计参考。
3. 遮挡与恢复逻辑参考。
4. RGB-D 融合策略参考。

它不适合直接替换现有 `360VOT + HiT + DTC` 架构。
